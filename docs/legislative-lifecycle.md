# 입법 라이프사이클 가이드

> assembly-api-mcp v0.7.0부터 국회(의안정보) + 국민참여입법센터 + 국회예산정책처(NABO)
> 세 축의 Open API를 한 서버에서 통합 제공합니다. 이 문서는 각 API가 **입법 생애주기의
> 어느 단계**를 관측하는지, 왜 이들을 하나의 파이프라인으로 묶어 보는 것이 중요한지를
> 설명합니다.

## 1. 왜 통합하는가

기존에는 국회(의안정보시스템)와 행정부(국민참여입법센터, 관보 등), 그리고 국회 보좌조직인
국회예산정책처(NABO) 데이터가 각기 다른 사이트·별개 인증키·별개 UI로 파편화되어 있었습니다.
그 결과 정책 모니터링은 언제나 "반쪽짜리"였습니다.

정부 입법계획에서 출발해 입법예고 → 국회 발의 → 상임위 심사 → 본회의 통과 → 시행령·
하위 규칙까지 이어지는 **엔드투엔드(End-to-End) 입법 라이프사이클**은, 사실상 서로 다른
기관이 순차적·병렬적으로 생산하는 데이터를 이어 붙여야만 보입니다. assembly-api-mcp가
이 세 축을 하나의 MCP 서버(그리고 하나의 REST API 베이스)로 묶는 이유입니다.

## 2. 라이프사이클 단계별 API 매핑

### 1단계 — 태동기 (정부 입법계획)

정부 부처가 연간 어떤 법안을 추진할지 선언하는 시기입니다. 국회에 법안이 등장하기 수개월~
1년 전에 향후 규제 지형의 변화를 예측할 수 있는 **최초 신호**가 여기서 나옵니다.

| 축 | API | assembly-api-mcp 도구 |
|----|-----|----------------------|
| 정부 | 국민참여입법센터(입법계획) | `discover_apis` + `query_assembly` (Full 전용) |
| NABO | 경제·재정 사전 분석 리포트 | `get_nabo type=report` |

NABO의 선행 분석 리포트는 "이 법이 만들어질 것 같다"는 신호가 나오자마자 재정·거시경제
측면에서 어떤 파급이 예상되는지 미리 담고 있는 경우가 많아, 정책 형성 이전부터 이해관계자가
영향도를 수치로 추정할 수 있게 해줍니다.

### 2단계 — 형성기 (입법예고)

정부안의 구체적인 조문이 처음 공개되고 국민 의견을 수렴하는 시기입니다. 국회 논의가 정치적
쟁점화되기 전에, 이해관계자·전문가·기업 컴플라이언스 담당자가 **논리적 근거**를 붙여서
조문 수정을 이끌어낼 수 있는 **골든타임**입니다.

| 축 | API | assembly-api-mcp 도구 |
|----|-----|----------------------|
| 국회 | 진행중 입법예고 | `get_legislation_notices` |
| 정부 | 국민참여입법센터 입법예고 | `discover_apis` + `query_assembly` |
| NABO | 분야별 이슈 리포트 · 정기간행물 | `get_nabo type=report` / `type=periodical` |

### 3단계 — 심사기 (국회 발의 및 위원회 논의)

정부안과 의원 발의안이 병합 심사되고, 상임위·법사위·본회의 단계를 거쳐 표결됩니다. 정부안의
**원안이 어떻게 타협되고 변형되는지** 추적할 수 있는 단계입니다.

| 데이터 | assembly-api-mcp 도구 |
|--------|----------------------|
| 의안 검색·상세·접수이력 | `search_bills`, `get_bill_detail`, `get_bill_history`, `get_bill_review` |
| 제안자·소속 상임위·발의 정족수 | `analyze_legislator`, `search_members` |
| 위원회 회의록 | `search_meetings` |
| 본회의 표결 | `get_votes` |
| 주제별 다중 키워드 추적 | `track_legislation` |
| 국민동의청원 연계 | `search_petitions` |
| NABO 재정 추계·심사 대응 자료 | `get_nabo type=report` |

`track_legislation`으로 여러 키워드(예: "AI", "인공지능", "자동화 의사결정")를 한 번에 걸어
두면 정부 원안·의원 발의안·청원 3개 축이 한 화면에 모입니다. 여기에 `get_nabo`로 NABO
리포트를 얹으면 "이 법안이 **재정적으로** 말이 되는가"라는 세 번째 질문까지 함께 추적할 수
있습니다.

### 4단계 — 실행기 (행정예고 및 하위 법령)

법률이 통과된 후 실제 기술 세부사항과 가이드라인을 정하는 시행령·시행규칙·고시가 제·개정
됩니다. **진짜 규제의 세부 규정은 이 단계에서 확정**되는 경우가 많고, 모법과의 위임 구조를
추적하지 못하면 컴플라이언스가 빈틈을 드러냅니다.

| 축 | 데이터 | 도구 |
|----|--------|------|
| 정부 | 행정예고(관보) | 국민참여입법센터 통합 (`query_assembly` + `discover_apis`) |
| NABO | 사후 재정 영향 분석 | `get_nabo type=report` |
| NABO | 관련 분야 채용·인력 공고 | `get_nabo type=recruitments` |

## 3. 통합이 갖는 핵심 가치

### ① 자연어 인터페이스를 통한 입법·공공 데이터 민주화
276개 국회 API와 NABO·국민참여입법센터 API를 합쳐 총 **287개** 공식 엔드포인트를, MCP
프로토콜을 통해 **평문 한국어로 호출**할 수 있습니다. 270개가 넘는 API 명세서를 개발자가
직접 분석할 필요가 없어집니다.

### ② 할루시네이션 없는 신뢰성 높은 리걸테크
LLM이 실시간으로 국가 공식 API를 호출한 원본 데이터를 기반으로 답변을 생성하므로,
"진행 중인 법안이나 최신 의석수를 모른다"는 구조적 한계를 정면으로 해결합니다.

### ③ 입법 조사·법률 실무 생산성 극대화
기자·보좌관·로펌·컴플라이언스 담당자가 수일씩 만들던 '입법 동향 보고서'를 **분 단위**로
데이터 기반 자동화할 수 있습니다. `analyze_legislator`와 `track_legislation` 체인 도구는
단일 호출로 인적사항+발의법안+표결+NABO 관련 리포트까지 한 번에 묶어냅니다.

### ④ Agentic AI 시대의 시빅테크(Civic Tech) 선례
MCP(모델 ↔ 외부 세계 통신 표준)를 대한민국 공공 데이터에 전면 적용한 선도 사례입니다.
AI가 '공공 정책 비서'로서 도구를 들고 능동적으로 국회·정부·NABO 데이터베이스를 탐색하는
에이전트로 진화했음을 보여줍니다.

## 4. 통합 관측 아키텍처의 전략적 장점

### 사후 대응 → 선제적 정책 설계 전환
국회 발의 **이후**에 대응하면 이미 늦습니다. 국가 AI 전략 위원회급 거시 정책이나 신규 기술
산업의 방향 설정은 정부 입법계획 단계부터 개입해야 합니다. 기획 단계 정부 문서와 최종 국회
통과 법안의 **간극(Gap) 분석**을 AI로 자동화할 수 있게 됩니다.

### 국제 표준 ↔ 국내 행정 지침 정합성 확보
법률 자체는 선언적이지만, 실질적인 파급력은 행정예고의 '고시'·'가이드라인'에서 나옵니다.
AI 레드팀 운영 가이드, 웨어러블 기기 수면 모니터링 성능 평가 기준 같은 기술 요건은 대부분
행정부 규정으로 떨어집니다. 국회 법안(상위법)과 부처 행정예고(하위 규정)을 **동시에**
관찰하면 ISO/IEC 국제 표준 동향을 적기에 반영하고 위헌·위법 충돌을 차단할 수 있습니다.

### 이해관계자 충돌 예측 및 입법 리스크 최소화
산업 육성 계획(정부안)과 규제 강화 요구(의원 발의안·청원)의 충돌 구도를 입체적으로 관찰할 수
있습니다. 입법예고 단계 반대 의견이 상임위 회의록에서 어떻게 재등장하는지 맥락을 이어
읽으면 정성적 리스크 평가가 한 단계 고도화됩니다.

## 5. 3개 기관, 3개 인증키 — 현실적 제약

아쉬운 점 하나: 현재 체계에서는 세 개 사이트에서 각각 회원가입하고 세 개의 Open API 사용
승인을 따로 받아야 합니다.

| 기관 | 인증키 ENV | 발급 URL |
|------|-----------|---------|
| 열린국회정보 | `ASSEMBLY_API_KEY` | https://open.assembly.go.kr |
| 국민참여입법센터 (data.go.kr 경유) | `DATA_GO_KR_SERVICE_KEY` | https://data.go.kr |
| 국회예산정책처 NABO | `NABO_API_KEY` | https://www.nabo.go.kr/ko/api/apply.do?key=2509230004 |

assembly-api-mcp는 세 키를 한 번에 받아서 **하나의 MCP 서버 / 하나의 REST API 루트**로
노출합니다. 장기적으로 정부 차원의 공공데이터 단일 인증 체계가 자리잡으면 이 제약도 사라질
것입니다. 그 전까지는 본 프로젝트가 사용자가 감당해야 할 운영 비용을 최소화하는 한 편법
역할을 합니다.

## 6. 요약

> **입법 라이프사이클 = 태동기(정부 입법계획) → 형성기(입법예고) → 심사기(국회 발의·심사) →
> 실행기(행정예고·하위 법령)**
>
> assembly-api-mcp v0.7.0은 이 네 단계 전체를 **단일 MCP 서버**로 관측 가능한 최초의
> 오픈소스 Civic Tech 인프라입니다. 국회의 276개 API, 국민참여입법센터 8개 API, 국회예산
> 정책처 3개 API — 도합 287개 공식 엔드포인트가 `get_nabo`, `discover_apis`,
> `query_assembly`, `track_legislation` 같은 자연어 친화 도구 뒤편에서 조용히 합류합니다.
